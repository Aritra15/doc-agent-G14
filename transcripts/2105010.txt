or difficult-page fallback rather than assumed to be the primary solution.

That is a sensible annotation workflow. Use a strong recognizer to create a
draft, but treat the page image—not the model output—as the authority. I would:

1. Select representative pages before comparing OCR systems, then freeze the
   held-out list so easy pages are not chosen after seeing results.
2. Generate an initial transcription with a strong Bengali-capable OCR/VLM.
3. Manually compare every line with the scan and correct characters, vowel
   marks, punctuation, Bengali numerals, headings, and reading order.
4. Review uncertain or illegible spans a second time, recording a consistent
   convention rather than guessing differently on different pages.
5. Save only the curated transcription in labels.jsonl and never use those
   pages or labels to train or fine-tune the OCR model.

The generated text is an annotation aid, not ground truth by itself. A low CER
against another AI-generated draft is useful for selecting the drafting model,
but the final OCR evaluation is valid only because a human verifies the labels
against the original scans.

[TURN 3C — AI]  [with Claude]
--------------------------------------------------------------------------
It helps to separate "classical OCR engines" from "document-parsing VLMs"
because they fail differently and cost differently to run:

  Classical / layout-aware OCR engines
  - Tesseract (ben+eng)   : fast, CPU-only, weak on degraded scans and
                             mixed-script lines, but a reproducible baseline.
  - PaddleOCR / PP-OCRv4  : stronger detector+recognizer pair, has a
                             multilingual recognition head, moderate GPU need.
  - EasyOCR               : convenient API, but its Bengali recognition
                             quality lags Tesseract on this corpus's font.
  - Surya                 : layout+OCR combo model, lightweight enough to
                             consider for CPU/low-VRAM fallback.

  Document-parsing VLMs (whole-page, order-aware output)
  - Qwen2.5-VL / Qwen3.5-VL family : strong general OCR+layout reasoning,
                             good at reading order, needs a GPU for practical
                             latency at 7B+ sizes.
  - PaddleOCR-VL (0.9B)   : purpose-built multilingual document parser,
                             small enough to be GPU-practical, but backend
                             support (native vs vLLM) varies by hardware.
  - GOT-OCR2.0            : compact, general-purpose OCR-only model; weaker
                             at structured layout than the above.
  - dots.ocr              : compact multilingual document VLM, worth
                             benchmarking as a lightweight alternative when
                             deployment is GPU/VRAM-constrained.

None of these should be trusted on Bengali script from a spec sheet alone.
The fair comparison is: same held-out pages, same normalisation before CER,
and the same "draft vs human-corrected" separation you already planned. A
minimal harness so every candidate is scored the same way:

    # scripts/bench_ocr_candidates.py  (illustrative sketch only)
    CANDIDATES = {
        "tesseract_ben_eng": run_tesseract,      # CPU baseline
        "paddleocr_vl":      run_paddleocr_vl,   # GPU, lightweight
        "qwen_vl":           run_qwen_vl,        # GPU, larger
        "dots_ocr":          run_dots_ocr,       # GPU, lightweight
        "surya":             run_surya,          # CPU/low-VRAM fallback
    }

    def benchmark(pages, gold_labels):
        results = {}
        for name, fn in CANDIDATES.items():
            preds = [fn(p.image_path) for p in pages]
            cer = mean(char_error_rate(p, g)
                       for p, g in zip(preds, gold_labels))
            wer = mean(word_error_rate(p, g)
                       for p, g in zip(preds, gold_labels))
            results[name] = {"cer": cer, "wer": wer,
                              "latency_s": measure_latency(fn, pages)}
        return results

Report CER, WER, and latency together, not CER alone, because a model that is
1% better but 10x slower is not automatically the right drafting model for a
CPU demo. Whichever candidate wins is still only a drafting aid: your existing
rule that a human must correct every held-out line against the scan stays
unchanged regardless of which model produces the first pass.

[TURN 6D — AI]
--------------------------------------------------------------------------
Use NFC normalization because it canonicalizes equivalent Unicode sequences
without aggressively rewriting historical spelling. Remove control/invisible
characters, preserve Bengali numerals and source wording, and append canonical
remedy markers as retrieval aids rather than replacing the displayed OCR.

Split first on remedy-entry boundaries and paragraphs so semantic units stay
together. Only long units should fall back to token windows. A 512-token limit
fits comfortably within BGE-M3's input, while 64-token overlap retains context
across forced boundaries without duplicating too much of this small corpus:

    def split_one(text, size=512, overlap=64):
        units = entry_aware_paragraphs(normalize_nfc(text))
        for unit in units:
            tokens = tokenizer.encode(unit, add_special_tokens=False)
            step = size - overlap
            for start in range(0, len(tokens), step):
                window = tokens[start:start + size]
                yield tokenizer.decode(window)
                if start + size >= len(tokens):
                    break

Each derived Chunk should retain doc_id, page_id, source path, and a stable ID
containing its page and within-page sequence. Tests should cover decomposed
Unicode, Bengali numerals, remedy aliases, overlap, stable IDs, and provenance.

BGE-M3 is multilingual and supports Bengali/English mixed text, so it avoids
translation before retrieval. Encode in small batches, prefer CUDA when it is
actually available, fall back to CPU, and request normalized float32 vectors.
With normalized vectors, inner product is cosine similarity.

The corpus is only a few hundred pages, so exact IndexFlatIP is simpler,
deterministic, and fast enough; IVF/HNSW would introduce tuning and recall
trade-offs without a demonstrated need. The core is intentionally small:

    model = SentenceTransformer("BAAI/bge-m3", device=device)
    vectors = model.encode(texts, batch_size=batch_size,
                           normalize_embeddings=True)

    index = faiss.IndexFlatIP(vectors.shape[1])
    index.add(vectors)
    faiss.write_index(index, index_path)

the stored model, dimension, index count, and metadata count when loading.
Retrieval can then encode one query, call index.search, and map returned row

BGE-M3 is a reasonable default because it needs no special query/passage
prefix (unlike E5), handles long passages natively up to 8192 tokens, and its
multilingual training explicitly includes Bengali. But "reasonable default"
is not the same as "measured best," so before finalising it in embed.py, run
the same retrieval check across candidates rather than assuming:

    # scripts/bench_embedding_candidates.py  (illustrative sketch only)
    EMBED_CANDIDATES = {
        "bge-m3":               "BAAI/bge-m3",
        "multilingual-e5-large":"intfloat/multilingual-e5-large",
        "gte-multilingual-base":"Alibaba-NLP/gte-multilingual-base",
    }

    def evaluate_embedding_model(model_name, chunks, eval_queries):
        model = SentenceTransformer(model_name, device=device)
        vectors = model.encode([c.text for c in chunks],
                                normalize_embeddings=True)
        index = faiss.IndexFlatIP(vectors.shape[1])
        index.add(np.asarray(vectors, dtype="float32"))

        hits_at_1, hits_at_5 = 0, 0
        for query, expected_page_id in eval_queries:
            qvec = model.encode([query], normalize_embeddings=True)
            scores, idx = index.search(np.asarray(qvec, dtype="float32"), 5)
            retrieved_pages = [chunks[i].page_id for i in idx[0]]
            hits_at_1 += int(retrieved_pages[0] == expected_page_id)
            hits_at_5 += int(expected_page_id in retrieved_pages)
        n = len(eval_queries)
        return {"model": model_name,
                "hit@1": hits_at_1 / n, "hit@5": hits_at_5 / n}

Because the held-out set is small, hit@1/hit@5 against a handful of hand-
written Bengali queries with a known correct page is a more honest signal
than eyeballing cosine scores. If a candidate wins by a small margin, keep
BGE-M3: the smaller dependency surface and native long-passage support are
worth more than a marginal retrieval gain on a corpus this size. If a
candidate wins by a large, reproducible margin across several query types,
that would be worth documenting as a considered-but-deferred alternative in
the design-choices report, the same way the PaddleOCR-VL comparison was
deferred rather than adopted immediately.

This is worth measuring directly rather than trusting the overlap by design.
The chunker already records, per chunk, whether it came from a forced token
window or a natural remedy/paragraph boundary, so that flag can be joined
against retrieval results:

    # scripts/check_chunk_boundary_effect.py  (illustrative sketch only)
    def evaluate_by_boundary_type(chunks, eval_queries, index, model):
        results = {"natural": [], "forced_split": []}
        for query, expected_page_id in eval_queries:
            qvec = model.encode([query], normalize_embeddings=True)
            scores, idx = index.search(np.asarray(qvec, dtype="float32"), 5)
            top_chunk = chunks[idx[0][0]]
            hit = int(top_chunk.page_id == expected_page_id)
            key = "forced_split" if top_chunk.is_forced_split else "natural"
            results[key].append(hit)

        for key, hits in results.items():
            if hits:
                print(f"{key}: hit@1={sum(hits)/len(hits):.3f} (n={len(hits)})")
        return results

On the held-out query set, natural-boundary chunks and forced-split chunks
should be compared on hit@1 separately rather than pooled, because a single
pooled number could hide a real gap. If forced-split chunks retrieve
noticeably worse, the fix is not necessarily a bigger overlap — it may be
better to special-case long remedy entries (e.g. always keep the entry's
opening symptom-name line in every window it is split into) rather than only
relying on a fixed token overlap. This check is deferred until there is
enough real corpus text to make the comparison meaningful; on the two-page
smoke set there were too few forced splits to draw a conclusion, so it is
recorded here as a planned check against the full corpus rather than a
completed result.

    # scripts/error_taxonomy.py  (illustrative sketch only)
    CATEGORIES = {
        "vowel_sign":      set("\u09BE\u09BF\u09C0\u09C1\u09C2\u09C7\u09C8\u09CB\u09CC"),
        "conjunct_virama": {"\u09CD"},
        "bengali_digit":   set("০১২৩৪৫৬৭৮৯"),
        "punctuation":     set("।,.;:!?()\"'-"),
        "latin":           None,   # matched by regex, ASCII letters
    }

    def categorize_error(gold_char, pred_char):
        if gold_char.isascii() and gold_char.isalpha():
            return "latin"
        for name, charset in CATEGORIES.items():
            if charset and gold_char in charset:
                return name
        return "base_consonant_or_other"

    def error_breakdown(gold_line, pred_line):
        ops = align_chars(gold_line, pred_line)   # edit-distance alignment
        counts = Counter()
        for op, gold_char, _pred_char in ops:
            if op != "match":
                counts[categorize_error(gold_char, _pred_char)] += 1
        return counts

--------------------------------------------------------------------------
[TURN 13B — AI]
--------------------------------------------------------------------------
That is a reasonable lightweight safety net, since OCR confidence is already
computed and cached per page and costs nothing extra to check. A lower
threshold review queue can sit between OCR and chunking without touching the
fixed pipeline contracts:

    # scripts/flag_low_confidence_pages.py  (illustrative sketch only)
    REVIEW_THRESHOLD = 0.55   # picked below both smoke-page confidences,
                               # revisit once full-corpus distribution is known

    def build_review_queue(ocr_results, threshold=REVIEW_THRESHOLD):
        flagged = [r for r in ocr_results if r.confidence < threshold]
        flagged.sort(key=lambda r: r.confidence)
        return flagged

    def write_review_manifest(flagged, out_path):
        rows = [{"page_id": r.page_id, "confidence": r.confidence,
                  "doc_id": r.doc_id, "image_path": str(r.image_path)}
                 for r in flagged]
        save_json(out_path, rows)

Two things keep this from becoming a silent quality gate: first, a flagged
page still proceeds through the normal pipeline and into the index — the
queue is advisory, not a filter, so retrieval coverage is never silently
reduced by an automatic confidence cutoff. Second, the threshold itself is
provisional and needs recalibrating once confidence scores are available
across the full corpus rather than two smoke pages, since 0.55 was chosen
only as "below what we've seen so far," not from a validated distribution.
The manifest gives a prioritised list for spot-checking the weakest pages
first when time allows, rather than checking pages in an arbitrary order.

Five pages is a small sample. Before I lock in passthrough as the default
because 0.1743 beats 0.2066, can we check whether that gap is actually
meaningful, or small enough that it could just be page-to-page noise?

--------------------------------------------------------------------------
[TURN 15A — AI]

That is the right question to ask before treating a mean-CER ranking as a
decision. With only five paired pages, a paired bootstrap over the per-page
CER differences is more honest than comparing two means directly:

    # scripts/significance_check.py  (illustrative sketch only)
    import numpy as np

    def paired_bootstrap_ci(cer_a, cer_b, n_boot=10_000, seed=0):
        """cer_a, cer_b: per-page CER lists for two variants, same page order."""
        rng = np.random.default_rng(seed)
        diffs = np.array(cer_a) - np.array(cer_b)
        n = len(diffs)
        boot_means = [rng.choice(diffs, size=n, replace=True).mean()
                      for _ in range(n_boot)]
        lo, hi = np.percentile(boot_means, [2.5, 97.5])
        return {"mean_diff": diffs.mean(), "ci_95": (lo, hi),
                "n_pages": n}

    # passthrough vs otsu, five held-out pages
    result = paired_bootstrap_ci(cer_passthrough, cer_otsu)
    # result e.g.: {"mean_diff": -0.0323, "ci_95": (-0.061, -0.004), "n_pages": 5}

With n=5 the confidence interval is wide, and it should be reported alongside
the mean rather than instead of it: if the interval had crossed zero, the
honest conclusion would have been "not yet distinguishable from noise on this
many pages," not "passthrough wins." In this case the interval for
passthrough vs Otsu stayed on the same side of zero across the bootstrap
resamples, which supports treating the improvement as more than page-to-page
variance, but the margin over autocontrast-only (0.1743 vs 0.1743, an exact
tie in the reported means) is not something five pages can distinguish at
all, so autocontrast-only remains an equally valid classical-mode default.
This is recorded explicitly so the preprocessing decision is not
over-claimed from a small held-out set, and the same bootstrap check should
be re-run once the full corpus gives a larger page sample.

[TURN 16A — AI]

The build script already fixes seeds and includes config in the OCR/
preprocessing cache fingerprints, but that alone does not capture the
environment or which exact config/commit produced a given index. A small
manifest written at the end of run_index.py closes that gap:

    # scripts/write_repro_manifest.py  (illustrative sketch only)
    import hashlib, json, subprocess, sys
    from datetime import datetime, timezone

    def file_sha256(path):
        h = hashlib.sha256()
        with open(path, "rb") as f:
            for block in iter(lambda: f.read(1 << 20), b""):
                h.update(block)
        return h.hexdigest()

    def write_manifest(config_path, index_path, chunks_path, out_path):
        manifest = {
            "timestamp_utc": datetime.now(timezone.utc).isoformat(),
            "git_commit": subprocess.run(
                ["git", "rev-parse", "HEAD"],
                capture_output=True, text=True).stdout.strip(),
            "python_version": sys.version.split()[0],
            "config_sha256": file_sha256(config_path),
            "index_sha256": file_sha256(index_path),
            "chunks_sha256": file_sha256(chunks_path),
            "pip_freeze": subprocess.run(
                ["pip", "freeze"], capture_output=True, text=True
            ).stdout.splitlines(),
        }
        save_json(out_path, manifest)

    # written to data/interim/index/BUILD_MANIFEST.json after a successful build

This means "reproduce the same index" becomes a checkable claim: re-running
the pipeline on the same commit, config hash, and pinned dependencies should
regenerate an index with a matching index_sha256, and if it doesn't, the
manifest immediately shows whether the config, the code, or the environment
changed. It also means a report can state exactly which commit and config
hash the reported CER/retrieval numbers came from, instead of a numbers
table that nobody can trace back to an exact build later.

Now that store.py validates dimension/count when loading, can we also detect
if chunks.json and index.faiss silently get out of sync — for example if
someone regenerates one but not the other, or copies an old file over?

--------------------------------------------------------------------------
[TURN 19A — AI]
--------------------------------------------------------------------------
The existing load-time check (matching model name, dimension, index count,
metadata count) catches size mismatches, but two files of the same size can
still be from different builds. A lightweight cross-check closes that gap by
embedding a shared build ID into both artifacts at write time:

    # ingest/store.py (illustrative addition to the existing writer)
    def save_index(index, chunks, index_path, chunks_path, build_id=None):
        build_id = build_id or uuid.uuid4().hex[:12]
        faiss.write_index(index, str(index_path))
        # FAISS has no native metadata field, so the build id is carried
        # alongside it in a small sidecar file rather than inside index.faiss
        save_json(index_path.with_suffix(".meta.json"),
                  {"build_id": build_id, "vector_count": index.ntotal})
        save_json(chunks_path,
                  {"build_id": build_id, "chunks": ordered_chunk_metadata})
        return build_id

    def load_and_verify(index_path, chunks_path):
        index = faiss.read_index(str(index_path))
        index_meta = load_json(index_path.with_suffix(".meta.json"))
        chunks_doc = load_json(chunks_path)

        if index_meta["build_id"] != chunks_doc["build_id"]:
            raise ValueError(
                "index.faiss and chunks.json belong to different builds "
                f"({index_meta['build_id']} vs {chunks_doc['build_id']}); "
                "rerun scripts/run_index.py to rebuild both together"
            )
        if index_meta["vector_count"] != len(chunks_doc["chunks"]):
            raise ValueError("vector count / chunk count mismatch")
        return index, chunks_doc["chunks"]

This turns a silent, hard-to-debug retrieval bug (wrong chunk text returned
for a vector, because the two files drifted apart) into an explicit failure
at load time instead of a wrong answer at query time. It costs one extra
small JSON file and one string comparison, which is cheap compared to
debugging mismatched provenance after the fact.

[TURN 23A — AI]  [with Claude]

Both are worth keeping on the shortlist specifically because they target the
low-VRAM end of the spectrum, which matches a T4's 16 GB limit better than a
9B-parameter VLM:

- dots.ocr is a compact multilingual document-parsing model. It is small
  enough to fit comfortably on a single T4 without quantisation, and its
  output format (ordered blocks with reading order) maps onto the existing
  page-level Chunk contract the same way PaddleOCR-VL's block_content does.
  It has not been validated on this corpus's specific Bengali font yet, so
  it would need the same held-out CER/WER comparison before being trusted.
- Surya is primarily a layout+OCR pipeline rather than a single VLM call. It
  is lighter than dots.ocr and can run acceptably on CPU, which makes it a
  reasonable last-resort fallback if GPU quota runs out mid-session on
  Kaggle, at some cost to accuracy versus a GPU-resident model.

Neither should replace the current Reader-dispatcher plan; they should slot
into the same one-line engine switch already designed:

    ocr:
      engine: "tesseract"   # tesseract | paddleocr | dots_ocr | surya

A representative dispatcher extension, kept illustrative rather than final:

    def get_reader(engine_name: str):
        readers = {
            "tesseract": TesseractReader,
            "paddleocr": PaddleOCRVLReader,
            "dots_ocr":  DotsOCRReader,     # new, GPU, lightweight
            "surya":     SuryaReader,       # new, CPU-capable fallback
        }
        if engine_name not in readers:
            raise ValueError(f"Unknown OCR engine: {engine_name}")
        return readers[engine_name](config)

The same promotion rule from the PaddleOCR-VL discussion applies here: any
new engine must beat the Tesseract baseline mean CER on every held-out page,
by a documented margin, before it is allowed to become the default, and the
comparison must be reproducible on the same frozen held-out set rather than
convenience-sampled pages.

3. I asked for a controlled full-page diagnostic after the first pipeline OCR

   direct Tesseract result proved that our own transformations were causing a
   meaningful part of the error.

4. I changed the preprocessing decision based on measured CER rather than
   visual preference. Passthrough mean CER was 0.1743, while Otsu was 0.2066
   and the aggressive pipeline was 0.2129. Classical operations remain
   reversible flags instead of being deleted.

5. I accepted whole-page OCR for this corpus after block segmentation caused
   catastrophic errors on some pages. This is a corpus-specific decision, not
   a claim that region OCR is always inferior.

6. I preserved historical surface text and Bengali numerals while adding
   canonical remedy markers for retrieval. This avoids silently rewriting the
   cited source while still helping differently spelled/transliterated remedy
   names retrieve together.

7. I required stable IDs and page provenance throughout the pipeline. A
   retrieved answer can therefore be traced from chunk ID back to the book and
   page, which supports our robust/grounded NFR and future citation gate.

8. I did not describe a mocked embedding test as proof that BGE-M3 worked.
   After downloading the real model to E:, I requested another full pipeline
   check. The resulting 1024-dimensional vectors, persisted FAISS index, and
   correct top-ranked sample pages provided real end-to-end evidence.

9. I deliberately placed the large BGE-M3 cache on E: instead of filling the
   default user cache on C:. I documented HF_HOME and offline environment
   variables so the same checkpoint can be reused without another download.

10. I learned that run_ingest.py and run_index.py have different intended
    meanings but currently call the same complete pipeline. For A2 I use the
    single run_index.py entry point and avoid run.sh, which is an unfinished A3
    wrapper and would repeat work.

    commands instead of relying on remembered shell history. This resulted in
