# A2 — Build the Knowledge Base

## Project: BanglaHomeoRAG

A2 is the first implementation milestone.  
The goal is to turn the scanned Bengali homeopathy books from A1 into a **searchable knowledge base**.

In simple terms:

**Scanned pages → preprocessing → OCR → normalization → chunking → embeddings → vector index → retrieval test**

By the end of A2, the system should be able to take a question and retrieve the most relevant page/chunk from the corpus.  
The full answering agent is built later in A3.

## 3. Build and Compare the Main Components

A2 requires real implementation decisions for the following stages.

### OCR

Convert scanned page images into text.

Planned choices from A1:

- Baseline: Tesseract 5 Bengali OCR
- Possible fallback: Bangla-aware TrOCR / Surya for difficult pages

For difficult scans, preprocessing may include:

- deskewing
- denoising
- Sauvola adaptive binarization

At least one pretrained method should actually be run and evaluated, not only mentioned.

### Text Normalization

Clean the OCR output while preserving medically important information.

Important steps:

- Unicode normalization
- preserve Bengali numerals such as `৬/৩০/২০০`
- remove obvious OCR garbage
- handle old Bengali orthography
- canonicalize remedy-name variants

Example:

```text
ভিরেট্রাম
ভেরাট্রাম
Veratrum
        ↓
veratrum_album
```

### Chunking

Split the OCR text into searchable pieces.

Preferred strategy:

- one remedy entry / meaningful medical entry per chunk

Fallback:

- fixed-size chunks, e.g. ~512 tokens with overlap

The purpose is to keep a medicine name, symptoms, potency and dose together whenever possible.

### Embeddings

Convert every text chunk into a numerical representation for semantic search.

Possible multilingual choices from A1:

- BGE-M3
- LaBSE

The chosen model should work well with Bengali and mixed-script text.

### Vector Index

Store the embeddings so they can be searched efficiently.

A suitable choice for this corpus is something such as:

- FAISS Flat index

The final choice should be justified using corpus size and retrieval requirements.

## 4. Build the Actual Knowledge Base

Each stored chunk should keep its source information.

Example structure:

```text
page_id: bk2_p170
chunk_id: bk2_p170_c03
text_norm: "কলেরা ... ভিরেট্রাম ... ৬ ৩০ ২০০ ..."
remedy_ids: [veratrum_album]
ocr_conf: 0.81
```

After embedding and indexing, a Bengali query should retrieve the most relevant chunk/page.

Example flow:

```text
Question
   ↓
Embedding
   ↓
Vector search
   ↓
Relevant chunk
   ↓
Original book + page
```

# Recommended Implementation Order

1. Download and organize the scanned books.
2. Prepare page images.
3. Run image preprocessing.
4. Run Bengali OCR.
5. Create the manually transcribed OCR evaluation set.
6. Measure OCR quality.
7. Normalize Bengali text and remedy names.
8. Implement entry-aware chunking.
9. Generate multilingual embeddings.
10. Build the vector index.
11. Run retrieval queries.
12. Record successful and failed examples.
13. Collect index/OCR statistics.
14. Fill the A2 form using the **actual results**.

# Main Focus for BanglaHomeoRAG

The most important technical issues in A2 are:

- Bengali OCR quality
- old Bengali orthography
- mixed Bangla/Latin remedy names
- Bengali potency numerals
- remedy-name canonicalization
- entry-aware chunking
- preserving page-level provenance for citation
- retrieving the correct medical passage instead of merely a similar one

---

# Final Goal of A2

At the end of A2, we should have:

> **A reproducible pipeline that converts the historical Bengali scanned books into clean, structured, searchable chunks and can retrieve the correct source page for a query, with measured OCR and retrieval performance.**

A2 is therefore mainly about **building and validating the knowledge base**.  
The reasoning/answer-generation agent comes in **A3**.
